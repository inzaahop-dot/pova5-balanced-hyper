# C4 — План тестирования и восстановления

| Поле | Значение |
| --- | --- |
| ID | `C4-VALIDATION-PLAN` |
| Статус | `BLOCKED` (до G2 и G3) |
| Волна | W4 |
| Зависимости | C2, C3 |
| Владелец | Роль QA/безопасности |
| Разрешение на работу с устройством | **НЕ ПОЛУЧЕНО** |

## Цель

Подготовить проверяемую матрицу тестов и план восстановления, которые доказывают обратимость модуля и предотвращают случайное изменение устройства.

## В объём входит

- Слои проверок от статического разбора до read-only smoke.
- Критерии прохода/остановки и наблюдаемые признаки регресса.
- Recovery runbook как инструкция, не как выполненный откат.
- Правила сбора и маскирования доказательств.

## В объём не входит

- Выполнение проверок в рамках текущего коммита.
- Прошивка, сброс до заводских настроек, разблокировка загрузчика.
- Изменение системных APK и настроек безопасности.

## Матрица тестов (план)

| Слой | Что проверяется | Среда | Изменения на телефоне |
| --- | --- | --- | --- |
| L0 | Документы, MECE-границы, статусы артефактов | Репозиторий | Нет |
| L1 | Структура module, манифест, синтаксис скриптов, хеши своих файлов | Локальная песочница | Нет |
| L2 | Совместимость RRO/ресурсов с API 34 и arm64-v8a | Изолированная тестовая среда | Нет |
| L3 | Read-only состояние overlay и UI после apply **только по отдельному разрешению** | Целевое устройство | Только через одобренный module |
| L4 | Откат: disable → uninstall → reboot → сравнение с baseline | Разрешённая тестовая среда | Восстановление стока |
| L5 | Поведение после OTA и при конфликте модулей | Тестовая среда | Нет на целевом устройстве |

> L3/L4 остаются спроектированными, пока не получено явное разрешение.

## Наблюдаемые признаки

- Устройство завершает загрузку в ожидаемое время.
- `cmd overlay list` и `dumpsys overlay` согласованы с ожидаемым списком модуля.
- Отсутствуют новые сбои в системных UI-компонентах.
- После `revert` собственные overlay модуля больше не перечисляются.
- Ни один системный APK не отличается по хешу от baseline (сравнение только если baseline законно собран).
- Ни один параметр безопасности не изменялся.

## Критерии остановки

- Изменён Verified Boot, SELinux, bootloader или состояние block-устройств → STOP.
- Обнаружен чужой системный APK/overlay без владельца → STOP.
- Модуль требует запись вне своего каталога → STOP.
- Есть признаки bootloop или потери UI → STOP и переход к runbook.
- Запрошен дамп раздела, APK прошивки или персональные логи → отказать.

## Recovery runbook (проект)

1. Прекратить все запланированные apply/тесты.
2. Отключить модуль в root-менеджере через его пользовательский интерфейс.
3. Выполнить `revert` модуля, если он доступен и не требует записи вне своего каталога.
4. Удалить только каталог модуля.
5. Перезагрузить устройство и сравнить read-only состояние с baseline.
6. Если загрузка не восстанавливается — использовать штатные средства восстановления **только после отдельного разрешения**; не прошивать и не стирать данные без него.
7. Зафиксировать факт инцидента без персональных данных и без дампов прошивки.

## Правила доказательств

- Разрешены: команда, дата, краткий результат с маскированием, хеши собственных артефактов.
- Запрещены: полные `logcat`/`dumpsys`, дампы разделов, копии системных APK, ключи и секреты.
- `REPORT.md` не создаётся до реальных проверок; результаты фиксируются ниже.
- Статус `PASS` присваивается только после реального прогона.

## Definition of Done

- [ ] Матрица содержит L0–L5 и ожидаемый результат каждого слоя.
- [ ] Для каждого стоп-критерия есть действие.
- [ ] Runbook удаляет только каталог module.
- [ ] Нет операций прошивки, сброса, разблокировки или изменения настроек безопасности.
